# Windows Hello: требования к исследованию интеграции

## Текущее состояние

Windows-клиент разблокирует мастер-ключ отдельным паролем восстановления. Сохранения ключа с защитой Windows Hello пока нет. При проверке на рабочем компьютере обнаружена обычная USB-камера; её совместимость с Windows Hello не установлена. Наличие камеры само по себе не подтверждает доступность распознавания лица.

Android использует другой механизм: ключ для локальной копии защищён Android Keystore и подтверждением сильной биометрии на совместимом устройстве. Одинаковый мастер-ключ на разных устройствах получается через пароль восстановления, а не из биометрического образца.

## Ограничения известных API

[Windows Hello KeyCredentialManager](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello) создаёт ключевую пару устройства и позволяет подписать запрос после подтверждения Windows Hello. Документация описывает аутентификацию с помощью подписи; её недостаточно для вывода, что тот же API безопасно расшифровывает локальную копию произвольного мастер-ключа. Windows Hello также может предложить PIN, поэтому успешная проверка сама по себе не доказывает, что использовано лицо.

[UserConsentVerifier](https://learn.microsoft.com/en-us/uwp/api/windows.security.credentials.ui.userconsentverifier) возвращает результат подтверждения пользователя. Если просто показать этот диалог, а затем расшифровать мастер-ключ обычным DPAPI, проверка интерфейса сама по себе не связывает доступ к ключу с подтверждением: процесс под той же учётной записью может попытаться вызвать DPAPI самостоятельно. Такую схему нельзя представлять как криптографически защищённую Windows Hello разблокировку.

[Политика пользовательского интерфейса CNG](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/ns-ncrypt-ncrypt_ui_policy) описывает требования к диалогу для ключа, но для выбора механизма необходимо отдельно проверить поддерживаемые провайдером операции, допустимые методы подтверждения, требования к TPM и фактическую семантику защиты. Наличие флага диалога не является доказательством обязательной проверки лица.

## Условия реализации и проверки

1. Выбрать и документировать механизм, который криптографически ограничивает использование ключа или получение материала для расшифровки, а не только показывает диалог. Сохранить модель клиентского шифрования и восстановление отдельным паролем.
2. Подтвердить по документации и экспериментально, какие методы проверки допускаются на конкретной версии Windows и провайдере ключей; явно объяснить пользователю возможность PIN или другого резервного метода.
3. Проверить первую настройку, успешную и отменённую разблокировку, повторную разблокировку, блокировку сеанса, смену биометрии, удаление ключа, восстановление и работу без поддерживаемого датчика. Не удалять единственную рабочую копию мастер-ключа до успешной проверки нового способа.
4. Проверить атаки из другого процесса той же Windows-учётной записи, защиту при выходе пользователя и очистку ключа в памяти. Результаты проверки и оставшиеся границы безопасности описать отдельно; независимый аудит необходим до работы с реальными документами.

До выполнения этих условий приложение продолжает использовать пароль восстановления и не заявляет о биометрической защите Windows.
